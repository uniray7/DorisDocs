# 邊界審查 Checklist（Tech Lead / QA 視角）

給 Phase 4 使用。針對每個 feature spec，逐條檢查是否適用，適用的要寫出具體處理方式，不能只寫「已知風險」。

## 多租戶與資源隔離
- 租戶 A 是否可能透過 API/查詢看到租戶 B 的 metadata 或資料？
- 資源隔離失效時（例如共用 cluster 的情況），有沒有 noisy neighbor 防護（查詢併發數、記憶體、CPU 限制）？
- 租戶被刪除/停用後，殘留資料與權限是否確實清除？

## 配額與計費
- 使用者超過配額時，系統行為是什麼（拒絕新請求？降級？排隊？）？使用者會收到什麼樣的提示？
- 配額計算是否有 race condition（多個請求同時逼近配額上限）？
- 計費/用量統計若計算錯誤，是否有申訴/修正機制？

## 安全性
- 使用者輸入是否可能構成 SQL Injection（尤其是動態組出的查詢或 ingestion 的欄位對應）？
- API 是否有適當的身分驗證與授權檢查（避免 IDOR：用 ID 換掉存取別人的資源）？
- 機敏資料（PII）在日誌、錯誤訊息、監控系統中是否可能外洩？
- 服務帳號/API Key 若外洩，影響範圍與撤銷機制？

## Ingestion Pipeline 特有情境
- 網路逾時／連線中斷時，寫入是重試、丟棄、還是回報失敗？是否會造成重複寫入（需要冪等性設計）？
- Schema 演進（使用者改欄位型別/新增欄位）時，既有 pipeline 是否會中斷？如何通知使用者？
- 大量資料一次性匯入（backfill）是否會影響同 cluster 其他租戶的查詢效能？
- 髒資料/格式錯誤的資料如何處理（整批失敗 vs 部分成功 + 錯誤記錄）？

## 可用性與容錯
- 單一節點/元件故障時，使用者感受到的影響是什麼？是否符合 Phase 5 訂的 SLA？
- 服務維護/升級視窗是否會造成使用者查詢中斷？如何提前通知？

## 使用者體驗邊界
- 審核被拒絕時，使用者是否知道原因與如何補件？
- 服務長時間未使用（閒置）是否會被回收？回收前是否有通知？
- 使用者刪除自己的資源，是否有二次確認、是否可復原？
