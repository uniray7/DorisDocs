## 0. 給決策者的摘要

**請決策一件事**：self-managed 的 database 用什麼方式組織與承載用途宣告（§4）。

| 選項 | 內容 | 團隊建議 |
|------|------|---------|
| Option 1 | 只開三個固定 database | 不建議 |
| Option 2 | 自由開 database，強制 zone 命名 | 不建議 |
| Option 3 | 自由命名，用途在代建表單宣告 | **建議** |

**已定前提（§2）**：database 與 table 的 DDL 一律平台代建（先緊縮、後放寬）。

**一句話理由**：三個選項的管理能力與責任分工完全相同，差別只在「宣告」刻在結構裡、名字裡、還是表單裡；結構和名字改不了又裝不多，所以建議表單。

## 1. 背景

Self-managed 使用者原本的需求是「自己灌資料＋任意開 database／table」，平台原承諾 DDL 完全自由。釐清責任時發現三個問題：

1. **平台對看不懂的東西負不了責**：DDL 完全自由下，平台不知道有哪些物件、哪些重要，保留清除、健康巡檢等責任無處掛載。
2. **Replica 不是備份**：誤 `DROP TABLE`、灌錯資料會同時套用到所有 replica。這類邏輯錯誤靠 DR 處理（`internal/prd/ha-dr.md`，TBD-36）。
3. **保護性設定要在建表當下注入**：例如 replication 數，建錯了要等資料丟了才發現，所以 DDL 必須經過平台。

## 2. 已定前提（不在決策範圍）

1. **Database 與 table 的 DDL 一律走代建**：「提交 → 驗證 → 平台代建」，初期人工、之後做成工具；使用者帳號不授予任何 DDL 權限（帳號全由平台管理）。
2. **先緊縮、後放寬**：放寬是送禮、收回是毀約；先開放再收回是 breaking change。是否因 dbt 放寬見 §8 與 TBD-29。
3. **驗證深度**：語法＋危險操作攔截＋撞名＋保護性預設注入；**不驗 schema 設計**，品質責任在使用者。
4. **儲存健康巡檢涵蓋全部表**：代建擋的是建成時的品質，運行中的占用成長、compaction 積壓仍要巡檢（§6）。
5. **灌資料維持完全自由**：寫入路徑在使用者手上，這是 self-managed 的定義性特徵。

> ⚠️ 相對原承諾，DDL 的直接執行全面收回。Self-managed 與 managed 的差異改為「寫入路徑＋資料管理責任＋支援等級」，需管理層知悉。

## 3. 核心分析：zone 語義在 self-managed 是空心的

- Medallion（bronze／silver／gold）是組織慣例，引擎本身不附帶任何強制行為。
- Managed 的 zone 執行得了，是因為平台握著寫入路徑與 DDL（raw 只有平台 pipeline 能寫）。
- Self-managed 的寫入路徑在使用者手上：平台代建了表，仍無法保證資料照 zone 流動。
- **結論**：self-managed 的 zone 只是「宣告」。宣告用表單承載，資訊量更大、事後可改、免背命名規則。

## 4. 決策：database 組織方式

三個選項都走同一條代建管道，日常摩擦相同；差異在 database 的組織方式與用途宣告放在哪裡。

| | Option 1：固定兩庫 | Option 2：自由開＋命名規則 | Option 3：自由開＋表單宣告 |
|---|---|---|---|
| 做法 | 只開 `{ws}_raw`／`{ws}_curated` | 強制 `{ws}__{user_defined}__{zone}` | 自由命名；建庫、建表時在代建表單宣告保留期、敏感性、重要性等 |
| 組織自由 | ❌ 鎖死兩個庫 | ✅ | ✅ |
| 使用者負擔 | 資料全擠兩個庫 | 背命名規則；名字建立後不可改 | 表單多幾個欄位 |
| 宣告放在 | 結構（不可改） | 名字（不可改、資訊量小） | 表單（可改、資訊量大） |
| 主要缺點 | zone 語義空心，名實不符時責任更難釐清 | 與 Option 3 機制相同，命名規則是純摩擦 | 平台要維護宣告清冊 |
| R&R 差異 | 無 | 無 | 基準 |
| **建議** | 不建議 | 不建議 | ✅ |


**Option 3 的內容**：
- 建 database 時宣告保留期（平台執行清理，失敗告警）與敏感性（銜接 TBD-5、TBD-6）。
- 建 table 時在同一張表單宣告 TTL 覆寫、重要性等，涵蓋率 100%。
- 物件清冊由代建紀錄產生，並以 metadata 週期對帳；清冊對使用者可視。

## 5. R&R 矩陣（以 Option 3 為基準）

| 責任 | 平台 | 使用者 |
|------|------|--------|
| DDL 代建（驗證＋保護性設定注入） | ✅ 對執行結果與注入設定負責；預告執行時效 | 申請內容（schema、保留期、覆寫要求）的正確性 |
| 儲存健康巡檢（全部表） | ✅ best-effort 偵測＋告警；未告警不代表沒問題 | 收到告警後處置 |

| 保護性預設（replication 等） | ✅ 代建時注入＋cluster／database 級預設 | 明確要求壓低保護者，後果自負 |
| Schema 設計品質 | ❌ 不審不揹 | ✅ |
| 物件清冊 | ✅ | |
| 備份還原、誤刪救援 | 依 DR 規劃（TBD-36）；replica 擋不住誤刪 | 依 DR 規劃 |

| Row filtering／column masking | 待 TBD-5 | 政策內容 |

## 6. 平台對 cluster 穩定性的責任框架

代建擋得住 schema 類傷害，但寫入與查詢行為仍在使用者手上。穩定性以四層落實：

| 層 | 手段 | 性質 |
|----|------|------|
| 1. 事前攔截 | 代建驗證擋 tablet 爆炸、無分區大表、replication 違規 | 建成時的品質，全部表 |
| 2. 上限封頂 | Cluster／FE 級上限、磁碟水位保護、記憶體保護 | 引擎硬限制，全域生效 |
| 3. 偵測 | 儲存健康巡檢＋告警 | best-effort，不構成背書 |
| 4. 恢復與介入 | 系統層恢復＋緊急介入權 | 最後防線 |

**封頂的限度**：
- 保護存活、不保護效能：上限內的重度寫入與爛查詢仍會讓 cluster 全體變慢。
- 累積效應蓋不住：每張都合規的表加總，仍可能撐大 FE metadata、壓垮 compaction，要靠巡檢盯趨勢。
- 觸頂本身是使用者側事故：版本數超限拒寫（-235）、磁碟到 flood stage 整個 BE 停寫（同 BE 的正常表一起被拒）。對外文件必須預先說明。

**緊急介入權**（寫入對外使用規範）：偵測到危及 cluster 存活的行為時，平台可不經事先同意限制寫入、kill 查詢、極端時停用問題表，事後立即通知。

**對外承諾**：「弄不沉、劣化會叫、沉了會救、誰弄的有證據」；**不保證**使用者自己的行為不會讓查詢變慢。

## 7. 全代建的已知隱患與配套

| # | 隱患 | 配套 |
|---|------|------|
| 1 | 代建摩擦：所有 table DDL 都要申請，初期人工恐成瓶頸 | 預告執行時效（TBD-32）、支援批次提交；DDL 提交管道工具化的優先級提高 |
| 2 | dbt 需求可能很快出現 | 放寬預案已備妥（§8）；對外明示「目前不支援 dbt 直連建表，需求請透過 PM 提出」 |
| 3 | 巡檢的隱含責任：沒抓到時被指「巡檢失職」 | 對外寫明巡檢為 best-effort，不構成背書 |
| 4 | 運行中的傷害有時間差，可能在下輪巡檢前發生 | 封頂擋最壞情況＋高風險訊號加密巡檢；殘餘風險由 dedicated 隔離承擔 |

## 8. 放寬預案（需求觸發時的起點）

**觸發條件**：使用者正式提出 dbt／高頻建表需求。2026-11-19 起需求已浮現；是否開放、風險與可研究的防護見 `internal/prd/ddl-governance.md`（TBD-29）。

| 形態 | 機制 | 主要代價 |
|------|------|----------|
| A：雙軌制 | 平台代建為可選建議路徑（平台對建成當下的設定負責，ALTER 即責任轉移）；dbt 直連自建，平台零責任；巡檢涵蓋全部表 | 要做 drift 偵測、以 table id 追蹤 create-then-swap、清冊標示三種狀態；短命表會造成告警噪音 |
| B：全自建＋規範文件 | Table 全自建；平台發布「建表最佳實踐＋權責分界＋使用限制」，開通時確認、告警引用違反條款 | 防護靠文件與事後舉證；可研究引擎級 replication 強制設定補強 |
