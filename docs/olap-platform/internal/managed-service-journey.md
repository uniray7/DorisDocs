# Managed Service 端到端旅程：申請服務 → 建表 → 用量管理 → Tier 升級

> 目的：把四份獨立的 feature spec（workspace-application / database-table-application / quota-and-usage / cluster-tiering）串成一條使用者實際會走的路，檢查銜接處有沒有斷點或矛盾。
> 範圍：僅 **managed** 模式（self-managed 的對應流程見 `self-managed-operations.md`，機制完全不同，不在本文討論）。
> 定位：Phase 3/4 之間的整合檢查稿；核准後內容併入 `data-flow.md`（Phase 8）。

---

## 一、旅程總覽

```
① 申請服務（workspace-application）
   投影片 → 週三會議 → 核准 → staging 驗證 → 佈建
   佈建時：建 3 個 zone database + 依申請附的 schema 建「raw 初始表」
                                     │
                                     ▼
② 日常建表/改表（database-table-application）
   ws 成員 web console 提交 → 核准（方案 A/B）→ 平台系統執行
   （① 的初始表是唯一「不經過本流程」的例外，其餘全部走這裡）
                                     │
                                     ▼
③ 看用量（quota-and-usage）
   儀表板：儲存/QPS 占比、80% 早期預警、超標事件
                                     │
                    占用持續逼近或超過 tier 上限
                                     ▼
④ Quota 滿了拉高（cluster-tiering，即 tier 升級）
   TIER_CHANGE_REQUESTED → REVIEW → SCHEDULED → MIGRATING → VERIFYING → COMPLETED
   完成後回到 ②③，用新 tier 的配額繼續建表、看用量
```

**關鍵認知**：「申請 quota」不是獨立的第五個流程——quota 是 tier 的附帶產物，拉高 quota＝走④的 tier 升級。若團隊有「只想加儲存、不想連運算一起升」的需求，目前做不到（cluster-tiering.md 已知 open issue #1：儲存/運算未解耦，見四之 2）。

## 二、各階段銜接細節

### ① → ② 建表責任交棒

| 項目 | ① 申請服務（佈建時） | ② 日常建表 |
|---|---|---|
| 觸發 | 申請投影片附的 schema | ws 成員在 console 提交 |
| 核准 | 依方案 A/B（視為已核准 or 審核即核准） | 依方案 A/B（owner approve or 平台審核） |
| 執行者 | 平台系統（內部腳本） | 平台系統（自動執行） |
| 稽核紀錄 | ⚠️ **未定義**——見下方斷點 1 | `GET /ddl-requests`、`GET /schemas` 完整記錄 |

### ② → ③ 建表即時反映用量

- 建表時（database-table-application 行為規格 #6）已檢查「ws 儲存配額不足」並擋下，導向④；這代表 ② 對 ③ 的資料是**只讀查詢當下配額餘裕**，不是等 ③ 儀表板刷新才知道。
- 但 ③ 的儲存用量本身「非即時」（refresh 週期 ⚠️ 如每小時）——這代表 ② 的配額檢查用的是即時數字，③ 的儀表板顯示可能落後。兩者不衝突（②有自己的即時檢查路徑），但**對外文件要講清楚「申請當下的擋下判斷」與「儀表板看到的數字」可能有落差**，否則使用者會困惑「明明儀表板還沒滿，怎麼申請被擋」。

### ③ → ④ 誰觸發升級

- ③ 的 80% 預警、④ 的 80% 上限通知，**兩份文件各自描述了一次同樣的事件**——見下方斷點 2，需要你決定歸屬。
- 100% 之後的處置（限流/擋寫入）與「超標但不願升級」仍是待拍板 #4，兩份文件都正確地指向同一個待拍板項，沒有矛盾。

### ④ → ② / ③ 升級完成後回圈

- cluster-tiering.md 的遷移流程完成（COMPLETED）後，新 tier 的配額生效，② 的建表配額檢查與 ③ 的儀表板都應反映新上限——兩邊都沒有明確寫「tier 變更後配額數字何時更新」，✅ **但這屬正常實作細節（配額本來就跟 tier 掛勾，tier 變了配額自然變），不算斷點，列入待驗證即可。**

## 三、發現的斷點

### 斷點 1（可直接修）：「欠費」是已撤除的用詞，兩份文件漏改

2026-07-14 已決議「平台目前沒有任何付費機制，文件中『付費』措辭全數撤除」（`00-progress.md` Decision Log）。但這兩處還留著：

- `workspace-application.md`：`ACTIVE ⇄ SUSPENDED（違規/欠費/閒置，見 quota 與治理規範）`
- `workspace-isolation.md`：`suspend_ws(ws)` 說明含「欠費/違規/閒置」

這是決議沒套用到全部文件，不是新問題，我會直接修掉（拿掉「欠費」，SUSPENDED 觸發原因收斂為「違規/閒置」）。**如果你們其實還是想保留「用量超標不繳費/不升級」這種未來情境的觸發位置，跟現在的「欠費」意思不同，請告訴我，我會換個不含『付費』字眼的說法（例如「超標未處置」）而不是直接刪。**

### 斷點 2（需要你決定）：80% 早期預警，兩份文件都說是自己觸發的

- `cluster-tiering.md`：「系統對每個 ws 持續比對用量 vs tier 上限：≥80% 上限 → 通知 ws 負責人」
- `quota-and-usage.md`：「儲存占用達配額 80% → 儀表板標示 + 強制告警送聯絡人（cluster-tiering 早期預警）」

兩邊都描述了「同一個 80% 通知」，但沒有一份文件明講：**這個門檻判斷的計算邏輯放在哪個系統裡、另一邊只是引用結果**。如果實作時兩邊各自算一次，可能出現：算法不同步（一邊用 5 分鐘平均、一邊用即時值）、或使用者收到兩封重複告警。

這不是我能替你決定的事，因為它牽涉系統歸屬（哪個服務該擁有「用量 vs 上限」的比對邏輯），但我可以給你一個推薦方向：**quota-and-usage 負責計算與觸發**（它本來就是計量的資料基礎，儲存用量、QPS 都在它手上），**cluster-tiering 只負責接收「已超標」的事件、決定升級政策怎麼處理**（限流/通知/要不要主動觸發升級評估）。這樣職責清楚：quota-and-usage＝量測，cluster-tiering＝政策。要採用這個切法嗎，還是你們已經有別的系統設計想法？

## 四、其他待你留意（非斷點，僅提醒）

1. **① 佈建時建立的初始 raw 表，稽核紀錄怎麼補**：database-table-application 承諾「所有申請與執行留存稽核紀錄」「`GET /schemas` 可看版本歷史」，但初始表是內部腳本建的，不經過 `POST /ddl-requests`。若不補一筆對應紀錄，這張表在系統裡會「憑空出現」，日後追溯建表核准依據時查不到。建議：佈建腳本執行後，回寫一筆 `ddl-requests` 紀錄（來源標記為 `workspace-application`），讓 `GET /schemas` 的版本歷史從第一天就完整。
2. **儲存/運算解耦（open issue #1）**：目前 quota 是 tier 的附帶產物，沒有獨立調整空間。這不是本輪要解決的斷點，只是提醒——如果你等下要問「能不能只加 quota 不升 tier」，答案目前是不行，這條路徑要等 RFC 定案。
