## 1. 背景與動機

Self-managed 使用者的既有需求是「自己灌資料 + 任意開 database/table」，平台原承諾 DDL 完全自由。在釐清資料管理責任時發現三個矛盾：

1. **平台對看不懂的東西負不了責**。資料管理責任（保留清除、健康巡檢）需要平台至少知道「有哪些物件、哪些重要」。DDL 完全自由下平台既無物件清冊、也無語義，責任無處掛載。
2. **CCR 不是備份**。HA 是 cluster 級全同步——使用者誤 `DROP TABLE`、灌錯資料，standby 幾秒內同樣消失/污染。HA 擋機器故障，擋不住邏輯錯誤，這個 gap 必須被有意識地處理（→ §5 子決策）。
3. **保護性 config 需要下沉到 table 粒度**，但強制經手每次建表不可行——使用者以 **dbt** 處理資料，dbt 的運作方式即高頻 create/drop 暫時表（staging model、`__dbt_tmp` 中繼表、create-then-swap），全代建會讓 dbt 不可用（→ §2 雙軌制）。

## 2. 已定前提（團隊已收斂，不在決策範圍）

1. **Database DDL 一律走代建流程**：不直接打 Doris——「提交 → 驗證 → 平台代建」（初期人工執行，之後推出 API/GUI 工具）。database 是低頻操作，摩擦可接受。
2. **Table DDL 採雙軌制**（核心原則：**責任跟著建表路徑走**）：
   - **平台代建（建議路徑）**：事前攔截（語法＋危險操作＋撞名）＋保護性 property 注入（replication 等）＋事後告警（drift 偵測）。平台對**建成當下**的設定正確性負責。
   - **自建（直接打 Doris）**：dbt 等工具不受任何限制；**平台零責任**——replication property 設錯、retention 設錯等後果一律使用者自負。
3. **驗證深度**（database 與代建 table）：語法合法性＋危險操作攔截＋撞名檢查＋保護性預設注入。**不驗 schema 設計**——品質責任維持在使用者（既有決議不變）。
4. **儲存健康巡檢不分軌、涵蓋全部表**：目的是 **cluster 自保**——有問題的表不論出自哪條路徑都傷整座 cluster（詳見 §7 穩定性框架）。告警後的處置責任在使用者；對自建表的告警不構成背書。
5. **灌資料維持完全自由**（寫入路徑在使用者手上，這是 self-managed 的定義性特徵）。

> ⚠️ **對產品定位的影響**：相對原承諾「任意開 database/table」，只收回 **database 層的直接執行**；table 層維持完全自由（dbt 不受影響），「平台代建」是可選的保護路徑。Managed 與 self-managed 的差異重心維持在「寫入路徑＋資料管理責任」。
>
> ⚠️ **dbt 相容性注意**：dbt 慣以 schema（MySQL 協定下即 Doris database）組織 target，且會嘗試自動 `CREATE SCHEMA`——使用規範需指引「database 先透過代建流程建好、關閉 dbt 自動建 schema」（列入待驗證）。

## 3. 核心分析：為什麼 zone 語義在 self-managed 是空心的

這是主決策評估 Option 1/2 的關鍵：

- **Databricks 的 bronze/silver/gold（我們 tmp/raw/curated 的原型）本身不附帶任何引擎強制的管理行為**——medallion 是組織慣例，各層的管理行為全是採用團隊用 pipeline 工具與權限自己綁上去的。
- 我們 **managed 模式**的 zone 真的執行得了（tmp 只有 pipeline 能寫、raw 只有 merge SQL 能寫），唯一原因是**平台握著寫入路徑和 DDL**。
- **Self-managed 的寫入路徑在使用者手上**：平台無法要求 pipeline 只寫 raw、curated 只從 raw 衍生；使用者把黃金資料放 tmp，平台無從驗證。
- **結論**：self-managed 下 zone 是「宣告」不是「保證」。zone 能換到的只剩「按宣告套一包預設值」——而這件事用**表單宣告**承載，資訊量更大、事後可改、免背命名文法。**宣告制是實體，zone 命名只是它的一種介面，而且是最脆的一種。**

## 4. 主決策：治理形態三選項

> 共同前提「database 代建、table 雙軌」下，三個選項的日常摩擦幾乎相同；差異集中在 **database 的組織方式與語義承載**。

### Option 0（基線，已排除）：DDL 完全自由
維持原承諾、直接打 Doris。**排除理由**：無保護 property 注入點、無物件清冊、無宣告入口——資料管理責任完全無處掛載。列出僅為說明「為什麼需要這個決策」。

### Option 1：只開三個固定 database（`{ws}_tmp` / `{ws}_raw` / `{ws}_curated`）

| Pros | Cons |
|------|------|
| 與 managed 心智模型一致 | **Zone 語義空心**（§3）：給了結構卻保證不了語義，「名實不符」的責任糾紛更難釐清 |
| 物件盤點最整齊 | **組織粒度鎖死**：多資料域團隊全部擠三個庫 |
| 可按 zone 套預設值包 | 名字承載的宣告資訊量最小、且不可改 |
| | 命名形式（單底線）與 managed 慣例（雙底線）不一致，工具鏈要處理兩套 |

**團隊評估：不建議**——付出最大的自由度代價，換到的語義是空心的。

### Option 2：自由開 database，強制 `{ws}__{user_defined}__{tmp|raw|curated}` 命名

| Pros | Cons |
|------|------|
| 組織粒度自由 | Zone 語義同樣空心（§3） |
| 與 managed 命名一致，工具可共用解析邏輯 | 使用者要背命名文法；名字建立後不可改 |
| Zone 段可當宣告縮寫 | **與 Option 3 機制完全相同**——若平台不對 zone 附加差異化行為，命名規則就是純摩擦 |

**團隊評估：不建議**——與 Option 3 只差「宣告用名字載還是用表單載」；表單載得更多、可改、免文法。

### Option 3：自由開 database/table、無命名規則、代建流程＝宣告入口（**團隊建議**）

- **Database 建立時宣告**（內建在代建表單，皆可日後修改）：
  - **TTL/retention**：使用者指定保留期 → 平台檢查後執行清理，清理失敗/未生效時告警
  - **敏感性**：是否含敏感資料 → 銜接 open issue #3（row/column masking）與 PII 治理（open issue #5）
  - （備份宣告屬 §5 乙案，暫不提供）
- **Table 級宣告跟著建表路徑走**：代建表的宣告內建在表單；自建表可事後**選用登記**（dbt 暫時表無需理會，只登記重要長存表）。未登記的自建表僅受 database 級宣告與巡檢涵蓋。
- **物件清冊**：database 與代建 table 由流程紀錄產生（完整）；自建 table 由 metadata 週期掃描（近即時）。**清冊對使用者可視**（每張表標示：代建／自建／代建但已被變更）。

| Pros | Cons |
|------|------|
| 責任邊界最誠實：平台只承諾「執行宣告＋掉了會叫」，不假裝懂語義 | 與 managed 模型不一致（但本來就是兩種模式） |
| Database 級宣告內建必經流程、涵蓋率天然高；table 級選用登記不干擾 dbt | Table 級宣告涵蓋率取決於使用者自律 |
| 宣告可事後修改（名字不行） | 平台要維護宣告清冊系統 |
| 為 row/column masking（open issue #3）鋪好同一套宣告機制 | |

### 三選項比較

| | Option 1：固定三庫 | Option 2：自由開＋命名規則 | Option 3：自由開＋表單宣告 |
|---|---|---|---|
| Database 組織自由 | ❌ 鎖死 3 個 | ✅ | ✅ |
| 使用者額外負擔 | 組織受限 | 背命名文法 | 表單多幾個欄位 |
| 語義承載 | 固定結構（不可改） | 名字（不可改、資訊量小） | 表單（可改、資訊量大） |
| 語義可信度 | 宣告（空心） | 宣告（空心） | 宣告（**誠實承認**是宣告） |
| R&R 實質差異 | 無 | 無 | 基準 |
| 與 managed 工具鏈一致性 | 低 | 高 | 低（本來就是不同模式） |
| **團隊建議** | 不建議 | 不建議 | ✅ **建議** |

## 5. 子決策：備份/還原提供與否（兩案並列，**暫定甲**）

背景見 §1 矛盾 2（CCR 救不了邏輯錯誤）。此 gap 需被有意識地接受或補上：

| | **甲：不提供備份/還原（暫定採用）** | **乙：宣告制備份（保留為未來選項）** |
|---|---|---|
| 內容 | 平台不做任何備份；誤刪/誤操作/資料丟失**一律不救援**，使用者自行負責（含自建備份） | 使用者宣告「要備份、頻率、保留份數」→ 平台按宣告執行 Doris BACKUP 至 MinIO，監控備份 job 成功率（靜默失敗即告警） |
| 配套 | **舉證機制**：database 刪除有代建申請紀錄；table 級操作（含 DROP）與 DML 舉證依 **Doris audit log**（規劃集中至 ELK）——證據鏈完整，前提是 audit log 保存不可中斷（保留期 Phase 5/6 定）；對外文件**明文免責** | 責任切分：平台對「忠實執行宣告」負責；宣告內容正確性、未宣告物件的丟失歸使用者 |
| 成本 | 零開發、零維運 | 備份排程、還原流程、儲存空間、監控——需開發與常態維運 |
| 風險 | 第一個誤刪重要資料的使用者無法救援（免責擋得住責任，擋不住觀感） | 涵蓋率與宣告正確性的邊際糾紛；維運負擔 |

**啟動乙案的但書**：目前無備份相關計畫；待**平台有充足人力**且**使用者實際開出需求**時再評估投入（屆時以獨立提案增補，不影響本 RFC 其餘決議）。

## 7. 平台對 Cluster 穩定性的責任框架（四層防線）

必答的質疑：自建表、寫入行為、查詢行為都在使用者手上，平台怎麼對穩定性負責？答案**不是「全代建」**——建表只是傷害鏈的一環：寫入行為造成的 compaction 風暴、查詢行為的 IO 耗盡，跟表建得好不好無關。責任以四層落實：

| 層 | 手段 | 性質 | 涵蓋 |
|----|------|------|------|
| 1. 事前攔截 | 代建流程擋 schema 類毀滅傷害（tablet 爆炸、無分區大表、replication 違規） | 品質類——只作用於經手的表 | 僅代建表（選用） |
| 2. 上限封頂 | Cluster/FE 級上限參數、磁碟水位保護、記憶體保護 | **封頂類——引擎層硬限制，不經手也全域生效** | **強制，全部表** |
| 3. 偵測 | 儲存健康巡檢＋告警（含 CCR lag × 寫入量連動） | best-effort，不構成背書 | 全部表 |
| 4. 恢復與介入 | 系統層恢復（既有責任）＋**緊急介入權** | 最後防線 | 全 cluster |

### 封頂的三個限度（防止把第 2 層誤讀成完整保證）

1. **保護存活，不保護效能**：封頂是生死線不是品質線。上限內的爛表照樣污染 page cache、吃 IO 頻寬、造成 compaction 讀放大——cluster 活著但全體變慢。這是對外只承諾「弄不沉」、**明文不保證「不變慢」**的原因。
2. **累積效應蓋不住**：上限參數多為 per-表/per-tablet 粒度；一千張「每張都合規」的表加總仍可撐大 FE metadata、壓垮 compaction。總量治理靠第 3 層巡檢盯趨勢，封頂替代不了。
3. **觸頂本身是一場使用者側事故**：封頂以「讓越線操作大聲失敗」運作——版本數超限即拒寫（-235）、磁碟到 flood stage 整個 BE 停寫（**同 BE 上使用者自己的正常表一併被拒寫**）。這是防線正常運作而非平台故障，**對外文件必須預先說明觸頂行為**，否則第一次撞牆的使用者會當成平台事故來開戰。

### 緊急介入權（新增條款，須寫入對外使用規範）

巡檢偵測到**危及 cluster 存活**的行為（compaction 積壓即將全面拒寫、磁碟逼近水位、FE metadata 異常膨脹）時，告警等使用者處置來不及——平台可**不經事先同意**執行緊急處置：限制寫入速率、kill 失控查詢、極端時停用問題表；事後立即通知並說明依據。沒有這條，「平台對穩定性負責」與「使用者行為自由」在事故當下無法並存。

### 對外承諾的正確措辭

平台保證「**弄不沉**（封頂）、**劣化會叫**（巡檢）、**沉了會救**（恢復）、**誰弄的有證據**（audit log）」；**不保證**「使用者自己的行為不會讓查詢變慢」——告警到處置之間的受害窗口由使用者承擔。代建軌是使用者為單表買保險的**選項**，不是穩定性責任的基礎。

## 8. Table 雙軌制的已知隱患與配套

> 隱患為團隊分析；配套為建議案，隨本 RFC 一併會簽確認。

| # | 隱患 | 配套 |
|---|------|------|
| 1 | **代建表被後續 ALTER 污染責任邊界**：使用者有 table DDL 自由，也能改代建表——不處理會變成平台無限期背書 | 平台責任只到「建成當下設定正確」，**ALTER 即責任轉移**；巡檢做 drift 偵測（現況 vs 代建 baseline），被變更即告警＋清冊改標「代建但已被變更」 |
| 2 | **dbt 會讓代建表悄悄變自建**：dbt table materialization 是 create-then-swap，代建表交給 dbt 管，第一次 `dbt run` 後就是全新的自建表（名字不變、使用者無感） | 對外文件明文「**代建與 dbt 管理互斥**」；清冊以 Doris 內部 table id（非表名）識別，swap 後 id 變即自動改標自建＋通知 |
| 3 | **代建軌可能極少被用**：工作流以 dbt 為主（長存表也多是 dbt model），加上初期人工有等待，理性選擇是全自建 | 預期管理：代建軌定位為「重要長存表的建議選項」，人力配置勿高估使用率；提案核心價值（責任清晰）不依賴使用率 |
| 4 | **巡檢告警噪音**：dbt 高頻建刪的 `__dbt_tmp` 表在建置中天然呈現危險樣態，會淹沒真訊號 | 巡檢排除短命表（存活 < N 分鐘不評估）＋ pattern 白名單 |
| 5 | **巡檢的隱含責任**：沒抓到爛表、cluster 被拖垮時，使用者反咬「巡檢失職」 | 對外措辭寫死：巡檢為 best-effort 的 cluster 自保機制，未告警不代表沒問題、不構成背書 |
| 6 | **事後巡檢有時間差**：replication=1 大表、tablet 失控表可能在下輪巡檢前就造成傷害 | 第 2 層封頂把最壞情況擋住＋高風險訊號巡檢加密；殘餘風險由 dedicated 隔離承擔（傷到的只有自己）——此為 self-managed 限 dedicated 的又一理由 |
