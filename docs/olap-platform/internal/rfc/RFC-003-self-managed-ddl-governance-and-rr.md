## 1. 背景與動機

Self-managed 使用者的既有需求是「自己灌資料 + 任意開 database/table」，平台原承諾 DDL 完全自由。在釐清資料管理責任時發現三個矛盾：

1. **平台對看不懂的東西負不了責**。資料管理責任（保留清除、健康巡檢）需要平台至少知道「有哪些物件、哪些重要」。DDL 完全自由下平台既無物件清冊、也無語義，責任無處掛載。
2. **CCR 不是備份**。HA 是 cluster 級全同步——使用者誤 `DROP TABLE`、灌錯資料，standby 幾秒內同樣消失/污染。HA 擋機器故障，擋不住邏輯錯誤，這個 gap 必須被有意識地處理（→ §5 子決策）。
3. **保護性 config 需要下沉到 table 粒度**。全代建做得到這一點，但已預期使用者未來以 **dbt** 處理資料（dbt 的運作方式即高頻 create/drop 暫時表），與全代建不相容。權衡後採「**先緊縮、後放寬**」：現階段 DDL 一律代建（§2），dbt/高頻建表需求正式提出時啟動放寬預案（§9）。

## 2. 已定前提（團隊已收斂，不在決策範圍）

1. **Database DDL 一律走代建流程**：不直接打 Doris——「提交 → 驗證 → 平台代建」（初期人工執行，之後推出 API/GUI 工具）。database 是低頻操作，摩擦可接受。
2. **Table DDL 同樣一律走代建流程**（2026-07-17 改訂；含 CREATE/ALTER/DROP）：與 database 同一條「提交 → 驗證 → 平台代建」管道；使用者帳號**不授予任何 DDL 權限**（GRANT 落地與帳號體系的互動見 §8 隱患 3 與 §11）。平台因此對**所有表**做事前攔截與保護性 property 注入。
   - **為什麼先緊縮**：治理政策有不可逆的方向性——**放寬是送禮、收回是毀約**。先開放自建、等使用者的 workflow 長上去再收回，是 breaking change、政治成本極高；先緊縮、等需求明確再有依據地放寬，每一步都是給東西。
   - **已預期的未爆點**：使用者未來很可能以 **dbt** 處理資料（高頻 create/drop 暫時表、create-then-swap），與全代建不相容。此需求**正式提出**時，以 §9 放寬預案為起點討論，不另起爐灶。
3. **驗證深度**：語法合法性＋危險操作攔截＋撞名檢查＋保護性預設注入（replication 等）。**不驗 schema 設計**——品質責任維持在使用者（既有決議不變）。
4. **儲存健康巡檢涵蓋全部表**：目的是 **cluster 自保**——全代建擋的是「建成時」的品質，表的占用成長、compaction 積壓、tablet 健康是「運行中」的問題，仍需巡檢（詳見 §7 穩定性框架）。告警後的處置責任在使用者。
5. **灌資料維持完全自由**（寫入路徑在使用者手上，這是 self-managed 的定義性特徵）。

> ⚠️ **對產品定位的影響**：相對原承諾「任意開 database/table」，DDL 的直接執行**全面收回**（database 與 table 皆是）。Self-managed 與 managed 的差異重心改為「**寫入路徑（自建 pipeline）＋資料管理責任＋支援等級**」，不再包含 DDL 自由。此變更動到既有對使用者的承諾，需管理層知悉。

## 3. 核心分析：為什麼 zone 語義在 self-managed 是空心的

這是主決策評估 Option 1/2 的關鍵：

- **Databricks 的 bronze/silver/gold（我們 tmp/raw/curated 的原型）本身不附帶任何引擎強制的管理行為**——medallion 是組織慣例，各層的管理行為全是採用團隊用 pipeline 工具與權限自己綁上去的。
- 我們 **managed 模式**的 zone 真的執行得了（tmp 只有 pipeline 能寫、raw 只有 merge SQL 能寫），唯一原因是**平台握著寫入路徑和 DDL**。
- **Self-managed 的寫入路徑在使用者手上**：平台代建了表，仍無法要求 pipeline 只寫 raw、curated 只從 raw 衍生；使用者把黃金資料放 tmp，平台無從驗證。
- **結論**：self-managed 下 zone 是「宣告」不是「保證」。zone 能換到的只剩「按宣告套一包預設值」——而這件事用**表單宣告**承載，資訊量更大、事後可改、免背命名文法。**宣告制是實體，zone 命名只是它的一種介面，而且是最脆的一種。**

## 4. 主決策：治理形態三選項

> 共同前提「database＋table 全代建」下，三個選項的日常摩擦完全相同（都走同一條代建管道）；差異集中在 **database 的組織方式與語義承載**。

### Option 0（基線，已排除）：DDL 完全自由
維持原承諾、直接打 Doris。**排除理由**：無保護 property 注入點、無物件清冊、無宣告入口——資料管理責任完全無處掛載。列出僅為說明「為什麼需要這個決策」。

### Option 1：只開三個固定 database（`{ws}_tmp` / `{ws}_raw` / `{ws}_curated`）

| Pros | Cons |
|------|------|
| 與 managed 心智模型一致 | **Zone 語義空心**（§3）：給了結構卻保證不了語義，「名實不符」的責任糾紛更難釐清 |
| 物件盤點最整齊 | **組織粒度鎖死**：多資料域團隊全部擠三個庫 |
| 可按 zone 套預設值包 | 名字承載的宣告資訊量最小、且不可改 |
| | 命名形式（單底線）與 managed 慣例（雙底線）不一致，工具鏈要處理兩套 |

**團隊評估：不建議**——付出最大的自由度代價，換到的語義是空心的。

### Option 2：自由開 database，強制 `{ws}__{user_defined}__{tmp|raw|curated}` 命名

| Pros | Cons |
|------|------|
| 組織粒度自由 | Zone 語義同樣空心（§3） |
| 與 managed 命名一致，工具可共用解析邏輯 | 使用者要背命名文法；名字建立後不可改 |
| Zone 段可當宣告縮寫 | **與 Option 3 機制完全相同**——若平台不對 zone 附加差異化行為，命名規則就是純摩擦 |

**團隊評估：不建議**——與 Option 3 只差「宣告用名字載還是用表單載」；表單載得更多、可改、免文法。

### Option 3：自由命名、代建流程＝宣告入口（**團隊建議**）

- **Database 建立時宣告**（內建在代建表單，皆可日後修改）：
  - **TTL/retention**：使用者指定保留期 → 平台檢查後執行清理，清理失敗/未生效時告警
  - **敏感性**：是否含敏感資料 → 銜接 open issue #3（row/column masking）與 PII 治理（open issue #5）
  - （備份宣告屬 §5 乙案，暫不提供）
- **Table 建立時宣告**：全代建下宣告直接內建在建表表單（TTL 覆寫、重要性標記等），**涵蓋率天然 100%**，無需另設登記機制。
- **物件清冊**：全部物件由代建紀錄產生（完整、即時）；輔以 metadata 週期對帳，偵測繞道操作與紀錄遺漏。**清冊對使用者可視**。

| Pros | Cons |
|------|------|
| 責任邊界最誠實：平台只承諾「執行宣告＋掉了會叫」，不假裝懂語義 | 與 managed 模型不一致（但本來就是兩種模式） |
| 宣告內建於必經的代建流程，涵蓋率 100% | 平台要維護宣告清冊系統 |
| 宣告可事後修改（名字不行） | |
| 為 row/column masking（open issue #3）鋪好同一套宣告機制 | |

### 三選項比較

| | Option 1：固定三庫 | Option 2：自由開＋命名規則 | Option 3：自由開＋表單宣告 |
|---|---|---|---|
| Database 組織自由 | ❌ 鎖死 3 個 | ✅ | ✅ |
| 使用者額外負擔 | 組織受限 | 背命名文法 | 表單多幾個欄位 |
| 語義承載 | 固定結構（不可改） | 名字（不可改、資訊量小） | 表單（可改、資訊量大） |
| 語義可信度 | 宣告（空心） | 宣告（空心） | 宣告（**誠實承認**是宣告） |
| R&R 實質差異 | 無 | 無 | 基準 |
| 與 managed 工具鏈一致性 | 低 | 高 | 低（本來就是不同模式） |
| **團隊建議** | 不建議 | 不建議 | ✅ **建議** |

## 5. 子決策：備份/還原提供與否（兩案並列，**暫定甲**）

背景見 §1 矛盾 2（CCR 救不了邏輯錯誤）。此 gap 需被有意識地接受或補上：

| | **甲：不提供備份/還原（暫定採用）** | **乙：宣告制備份（保留為未來選項）** |
|---|---|---|
| 內容 | 平台不做任何備份；誤刪/誤操作/資料丟失**一律不救援**，使用者自行負責（含自建備份） | 使用者宣告「要備份、頻率、保留份數」→ 平台按宣告執行 Doris BACKUP 至 MinIO，監控備份 job 成功率（靜默失敗即告警） |
| 配套 | **舉證機制**：DDL（含 DROP database/table）皆有代建申請紀錄；DML 舉證依 **Doris audit log**（規劃集中至 ELK）——證據鏈完整，前提是 audit log 保存不可中斷（保留期 Phase 5/6 定）；對外文件**明文免責** | 責任切分：平台對「忠實執行宣告」負責；宣告內容正確性、未宣告物件的丟失歸使用者 |
| 成本 | 零開發、零維運 | 備份排程、還原流程、儲存空間、監控——需開發與常態維運 |
| 風險 | 第一個誤刪重要資料的使用者無法救援（免責擋得住責任，擋不住觀感） | 涵蓋率與宣告正確性的邊際糾紛；維運負擔 |

**啟動乙案的但書**：目前無備份相關計畫；待**平台有充足人力**且**使用者實際開出需求**時再評估投入（屆時以獨立提案增補，不影響本 RFC 其餘決議）。

> 註：全代建下 DROP 也經平台之手，驗證階段的危險操作攔截（二次確認）對誤刪多了一道防護；但確認後執行、資料即隨 CCR 同步消失，**不改變「無備份即無還原」的本質**。

## 6. R&R 矩陣（以 Option 3 為基準）

| 責任 | 平台 | 使用者 |

## 7. 平台對 Cluster 穩定性的責任框架（四層防線）

必答的質疑曾是「表、寫入行為、查詢行為都在使用者手上，平台怎麼對穩定性負責？」全代建（§2）回答了其中三分之一：schema 類毀滅傷害（tablet 爆炸、無分區大表、replication 違規）在建表時就被擋下。但**寫入行為與查詢行為仍完全在使用者手上**——compaction 風暴、IO 耗盡跟表建得好不好無關。穩定性責任以四層落實：

| 層 | 手段 | 性質 | 涵蓋 |
|----|------|------|------|
| 1. 事前攔截 | 代建驗證擋 schema 類毀滅傷害（tablet 爆炸、無分區大表、replication 違規） | 品質類——建成時的品質 | **全部表**（全代建） |
| 2. 上限封頂 | Cluster/FE 級上限參數、磁碟水位保護、記憶體保護 | **封頂類——引擎層硬限制，全域生效** | 強制，全部表 |
| 3. 偵測 | 儲存健康巡檢＋告警（含 CCR lag × 寫入量連動） | best-effort，不構成背書 | 全部表 |
| 4. 恢復與介入 | 系統層恢復（既有責任）＋**緊急介入權** | 最後防線 | 全 cluster |

### 封頂的三個限度（防止把第 2 層誤讀成完整保證）

1. **保護存活，不保護效能**：封頂是生死線不是品質線。上限內的重度寫入與爛查詢照樣污染 page cache、吃 IO 頻寬、造成 compaction 讀放大——cluster 活著但全體變慢。這是對外只承諾「弄不沉」、**明文不保證「不變慢」**的原因。
2. **累積效應蓋不住**：上限參數多為 per-表/per-tablet 粒度；一千張「每張都合規」的表加總仍可撐大 FE metadata、壓垮 compaction。總量治理靠第 3 層巡檢盯趨勢，封頂替代不了。
3. **觸頂本身是一場使用者側事故**：封頂以「讓越線操作大聲失敗」運作——版本數超限即拒寫（-235）、磁碟到 flood stage 整個 BE 停寫（**同 BE 上使用者自己的正常表一併被拒寫**）。這是防線正常運作而非平台故障，**對外文件必須預先說明觸頂行為**，否則第一次撞牆的使用者會當成平台事故來開戰。

### 緊急介入權（新增條款，須寫入對外使用規範）

巡檢偵測到**危及 cluster 存活**的行為（compaction 積壓即將全面拒寫、磁碟逼近水位、FE metadata 異常膨脹）時，告警等使用者處置來不及——平台可**不經事先同意**執行緊急處置：限制寫入速率、kill 失控查詢、極端時停用問題表；事後立即通知並說明依據。沒有這條，「平台對穩定性負責」與「使用者行為自由」在事故當下無法並存。

### 對外承諾的正確措辭

平台保證「**弄不沉**（封頂）、**劣化會叫**（巡檢）、**沉了會救**（恢復）、**誰弄的有證據**（申請紀錄＋audit log）」；**不保證**「使用者自己的行為不會讓查詢變慢」——告警到處置之間的受害窗口由使用者承擔。全代建使第 1 層涵蓋全部表，但它擋的是建表品質；寫入與查詢行為不經平台之手，「不變慢」依然無法承諾。

## 8. 全代建（緊縮政策）的已知隱患與配套

> 隱患為團隊分析；配套為建議案，隨本 RFC 一併會簽確認。

| # | 隱患 | 配套 |
|---|------|------|
| 1 | **代建摩擦 × 迭代速度**：table DDL 全部要申請（連 `CREATE TABLE AS` 做個中間表也是），self-managed 客群定位是「高客製、有能力自管」的團隊，建表頻率可能不低，初期人工執行恐成瓶頸、累積不滿 | 對外預告執行時效預期（如 N 個工作日內，Phase 5 定數字）；申請支援批次提交；**DDL 提交管道的 API/GUI 化優先級因此提高**（承載全部 DDL 流量） |
| 2 | **dbt 需求可能很快出現**：「等正式提出需求」可能上線初期即觸發（已知使用者以 dbt 處理資料的可能性高） | 放寬預案已完整分析備妥（§9）——觸發時執行預案、不重新吵一輪；對外文件明示「目前不支援 dbt 直連建表，有此需求請透過 PM 管道提出」，把需求逼到檯面上 |
| 3 | **權限收不乾淨則政策虛設**：政策的技術強制依賴「使用者帳號無任何 DDL 權限」。但既有前提是 self-managed「cluster 內帳號/權限自理」——**擁有 GRANT 權的使用者可以自己開回 DDL 權限**，兩者直接衝突 | 需擇一：(a) 初始帳號不含 GRANT_PRIV，帳號/權限管理收回平台代管（動到「帳號自理」前提，牽動 access-control spec）；(b) DDL 收回僅為**政策約束**（技術上可繞、繞了以 audit log 舉證＋違規處理）。**傾向 (a)**——緊縮政策靠自律執行等於沒有政策；列 §11 首要待驗證＋access-control 增修 |
| 4 | **巡檢的隱含責任**：沒抓到爛況、cluster 被拖垮時，使用者反咬「巡檢失職」 | 對外措辭寫死：巡檢為 best-effort 的 cluster 自保機制，未告警不代表沒問題、不構成背書 |
| 5 | **傷害主要來自運行行為，巡檢有時間差**：建表品質已由代建把關，但重度寫入造成的 compaction 積壓、占用暴衝可能在下輪巡檢前就造成傷害 | 第 2 層封頂擋最壞情況＋高風險訊號加密巡檢；殘餘風險由 dedicated 隔離承擔（傷到的只有自己）——此為 self-managed 限 dedicated 的又一理由 |

## 9. 放寬預案（已完整分析的備選形態，等需求觸發）

**觸發條件**：使用者**正式提出** dbt／高頻建表需求。屆時以本節為起點討論，不從零開始。

**為什麼現在不採用**：治理的不可逆方向性（放寬是送禮、收回是毀約——先開放再收回是 breaking change）；在沒有正式需求前，先取防護最強、責任最簡單的形態。以下兩個形態在 2026-07-16/17 的討論中已完整分析：

### 形態 A：雙軌制（代建＝有保護有責任／自建＝零責任）

- 機制：平台代建為**可選建議路徑**（事前攔截＋property 注入＋drift 告警，平台對建成當下設定負責、**ALTER 即責任轉移**）；自建（dbt 直連）平台**零責任**；巡檢不分軌涵蓋全部表。
- 當時已識別的隱患與配套（一併存檔）：代建表被 ALTER 污染責任邊界（→ 責任轉移＋drift 偵測＋清冊三態標示）；dbt create-then-swap 讓代建表悄悄變自建（→ 以 Doris 內部 table id 而非表名識別，swap 即改標＋通知）；代建軌恐極少被用（→ 定位為重要長存表的建議選項，勿高估使用率）；`__dbt_tmp` 短命表告警噪音（→ 巡檢排除存活 < N 分鐘的表＋pattern 白名單）。
- 額外工程成本：drift 偵測、table id 追蹤、清冊三態。

### 形態 B：全自建＋最佳實踐與權責文件

- 機制：table 全自建；平台發布「**Doris 建表最佳實踐＋權責分界＋使用限制**」對外文件，不遵照者自行承擔後果（replica 丟資料、效能、穩定性連帶）。
- 責任成立要件：開通時明確簽署/確認使用規範（申請會議加一項議程）；巡檢告警**引用違反的具體條款**＋時間戳；audit log 證據鏈。
- 防護補強：驗證 Doris 引擎級 replication 強制/下限 config（`force_olap_table_replication_num` 一類）——若 4.1 可用，等於把 property 注入下沉到引擎層，防護損失趨近零。
- 註：這份最佳實踐文件在任何放寬形態下都值得寫，屆時亦適用於 managed（見下）。

### 關聯：managed 模式 curated zone 的對應放寬（一併擱置）

曾討論在 managed 開放 curated zone 自由建表（供 dbt；tmp/raw 維持代建）：managed 的寫入路徑在平台手上、tmp/raw 語義是真的，「原料層平台保真、加工層使用者自由」這條線畫得住，且與 Databricks gold layer 的實際用法一致。**同「先緊縮」邏輯一併擱置**；屆時需先解決兩個前置問題：
1. Managed「備份還原/保留清除」承諾對自建 curated 表是否成立（傾向「責任跟著建表走」，但這動到 managed 的省事賣點，需管理層知悉）；
2. Shared cluster（tier 1）的**租戶互害爆炸半徑**——一個租戶的高頻建刪/tablet 膨脹傷及其他租戶，需以 Doris database 級 data/replica quota 圈住（待驗證）方可開放。
